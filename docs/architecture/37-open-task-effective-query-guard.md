# 37：开放式任务反复查日志——护栏升级 + 证据收口清单（Issue #90）

> 这篇不写逐段代码导读，只简单说明这次改了什么、为什么改、效果如何。

## 用大白话说

排查日志的开放式任务（t01/t06）之前老是步数耗尽，几乎都耗在「定位阶段反复查日志」。
原因是 `log_query` 一次只能查一个维度，要判断「外部扫描还是应用故障」得凑齐好几个维度的
证据，但模型常常查了又查、刹不住车。

这次做了两件事把它按住：

1. **把收尾标准从一句话变成清单**。原来系统提示词里只说「证据够了就收尾」，模型不听话。
   现在改成明确的四项清单：①按小时时间分布 ②按 service/路径分布 ③几条 404 明细样本
   ④发布记录（deploys.ndjson）对比。集齐这四项就直接给最终答案，别再多查。

2. **护栏从「数次数」改成「数有效次数」**。原来查询类工具（log_query / retrieve /
   runbook_search）连续调满 3 次就拦，但不管查得有没有用。现在：查出来是 0 条、或者
   参数跟上次一模一样，直接拦下并提示它收尾；只有真正带来新信息的查询才计入次数；
   读发布记录的 file_reader 也不再打断计数（之前是个漏洞，模型可以靠它重置计数绕过去）。

## 效果

同一套 24 次真实 DeepSeek 复测：

| 指标 | 之前 | 本次 |
| --- | --- | --- |
| 任务成功率 / 收敛率 | 19/24 (79.2%) | 23/24 (95.8%) |
| 步数耗尽（MAX_STEPS_EXCEEDED） | 3 | 1 |
| 解析失败（MODEL_OUTPUT_PARSE_ERROR） | 2 | 0 |
| 关键数字准确率 | 35/96 (36.5%) | 44/96 (45.8%) |

模型现在几乎每次都会主动列那四项证据，只剩一次 t02 步数耗尽。平均耗时从 15.9s 涨到
29.1s，主要是上一篇思考模式（36）让模型每条都先生成思考过程导致的，跟这次改动无关。
