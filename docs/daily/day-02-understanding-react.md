# Day 2：理解 ReAct

## 今天理解了什么

ReAct 的关键不是固定输出 `Thought`、`Action`、`Observation` 三个文本标签，而是建立一个有界、可观察的决策闭环：模型基于任务与已有观察作出决策；控制器把决策解析为最终回答或工具动作；工具结果以 Observation 回写状态；模型据此进入下一轮，直到正常完成或命中明确的终止条件。

各阶段需要保持清晰边界。模型只负责决策，不直接执行工具；解析器只负责把不可信的模型输出转换为结构化结果；工具注册表负责名称查找与参数边界；工具执行层统一返回成功或失败；循环控制器统一管理步数、路由和终止原因。这样才能分别测试解析失败、未知工具、工具异常和步数耗尽等分支。

原始 `ysymyth/ReAct` 更接近论文实验脚本：每个任务使用固定动作集合，notebook 通过文本标记、循环和环境反馈拼接轨迹。LangChain 与 LangGraph 则把消息、结构化工具调用、工具节点、状态路由、错误消息及运行控制提升为通用抽象。Self-ReAct 应学习它们的边界与状态设计，但暂不引入框架运行时，以免隐藏需要亲手理解的主循环。

## 遇到的问题与解决过程

### 问题

原始 ReAct 论文描述的是推理与行动协同的范式，作者仓库主要用于复现实验；成熟框架则包含持久化、中间件、人工介入和图执行等更高层能力。如果直接把三者等同，容易把任务脚本的偶然写法当作架构要求，或把成熟框架的全部能力提前搬入 MVP。

此外，错误分支不一定都应立即终止。未知工具或工具执行失败既可能是最终错误，也可能先作为 Observation 反馈给模型后恢复，需要区分“本轮结果”和“运行终止原因”。

### 解决过程

先从论文摘要与方法部分提取稳定语义：推理不直接改变环境，动作与环境交互，观察进入后续上下文。再对照作者 HotpotQA notebook 的实际循环，以及 LangChain/LangGraph 的模型节点、工具节点和条件路由，把论文语义映射为工程阶段。

最终约定：`ToolResult` 表达一次工具调用的成功或失败，`Termination` 表达整个运行结束的原因；可恢复错误先写回 Observation，由循环控制器结合错误策略和剩余步数决定继续或终止。最大步数则由控制器强制执行，不能依赖模型自行停止。
