# Day 10：最小系统提示词与输出格式契约

> Issue：[19 feat: 设计最小系统提示词与输出格式契约](https://github.com/fufufu11/Self-ReAct/issues/19)
>
> 本记录只描述 Day 10 的最小系统提示词：它把任务规则、工具清单和输出格式
> 契约渲染成一个确定性字符串。输出解析（Day 11）、Agent 主循环（Day 12）、
> 重试、流式和异步能力属于后续日期。

## 今天理解了什么

Day 7 建好了工具注册表，Day 8/9 有了三个真实工具，但模型还不知道"什么时候
可以用哪个工具、返回什么形状的答案"。系统提示词就是模型与框架之间的
**接线图**：它一方面告诉模型有哪些工具、各自做什么，另一方面约定模型必须
返回的 JSON 形状，让 Day 11 的解析器能机械地拆解，而不是猜。

两个决策形态来自 Day 4 的领域模型：`FinalAnswer`（最终回答）与 `ToolCall`
（工具调用）互斥，`kind` 字段是判别联合的"标签"。提示词用大白话把这两个
形状写清楚，等于把领域契约翻译给模型听。

提示词渲染必须是**确定性纯函数**：相同输入永远得到相同字符串。这样提示词
可被单元测试精确验证，也不会因为工具传入顺序不同而让模型看到不一样的
说明书。因此工具条目按名称排序，空描述用稳定占位符，空清单用固定说明。

另一个重要取舍是：提示词只消费工具的 `name` 与 `description`，不复制、不
解释工具行为。工具描述已经由各业务工具自己维护（Day 8/9），提示词照抄即可，
避免"提示词里的说明"与"工具实际行为"分叉。

## 设计边界与不变量

- **确定性**：相同工具清单输入两次渲染结果完全一致；工具按名称排序，与
  传入顺序无关；渲染不访问网络、不读取环境变量、不修改输入。
- **格式契约稳定**：无论工具清单如何变化，两种决策形态与输出规则都完整
  出现；`kind` 只能取 `"final_answer"` 或 `"tool_call"`，二者互斥。
- **消费最小接口**：提示词只读取工具的 `name` 与 `description`，不调用
  `execute`，不复制工具行为，避免描述与实现分叉。
- **空边界稳定**：工具描述为空时渲染 `（无描述）` 占位符；工具清单为空时
  渲染"当前没有可用工具。"并明确"只能输出 final_answer"，两种情况都不抛
  异常、不输出残缺格式。
- **输入纪律**：非序列输入、空名称或缺失名称的工具被明确拒绝，防止渲染出
  模型无法调用的残缺条目。

## 遇到的问题与解决过程

### 问题一：工具清单顺序怎么保证稳定

同一个工具集合如果按不同顺序传入，提示词会不同，模型看到的说明书就不
稳定。解决：`_normalize_tools` 把清单统一成 `(名称, 描述)` 列表，再按名称
排序。排序后"同集合、不同传入顺序"必然得到同一字符串，测试用正序与倒序
两次渲染断言相等。

### 问题二：工具描述为空或清单为空时怎么办

真实工具的 `description` 在注册时必须非空，但渲染函数自己不该假设调用方
永远守规矩。若描述为空就原样输出 `- name：`，模型看到的是残缺条目；直接
抛异常又太脆。解决：空描述渲染稳定占位符 `（无描述）`，空清单渲染
"当前没有可用工具。"，同时保留完整格式契约并明确"只能输出 final_answer"。

### 问题三：要不要在提示词里硬编码每个工具的参数字段

最省事的做法是把 `{"expression": ...}`、`{"path": ...}`、`{"query": ...}`
直接写进提示词模板。但这样提示词就和具体工具绑死了：将来加第四个工具，
提示词忘了更新，说明书就过时。解决：提示词不硬编码工具名或参数字段，只
写一条通用规则——`arguments` 的键名必须与对应工具描述中说明的参数一致，
描述里未出现的键会被工具拒绝。参数字段知识继续由各工具的 `description`
自己维护。

### 问题四：长 JSON 示例行超过代码宽度

工具调用契约里的 JSON 示例比 88 字符宽，直接写在一行会被 ruff 拦截。
解决：把该常量改成显式字符串拼接，把 JSON 示例拆成两段相邻字符串字面量，
渲染结果与原来完全一致，代码宽度也合规。
