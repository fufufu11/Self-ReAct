# Day 1：定义范围与开发规范

## 今天理解了什么

ReAct 的核心不是某个特定框架，而是一个持续迭代的闭环：模型先基于当前任务和已有观察进行推理或决策，然后选择并执行一个工具动作；工具执行结果会作为 Observation（观察）回写给模型，模型再据此决定下一步动作或给出最终回答。

这个闭环要求框架能够清楚地管理任务状态、工具调用结果和终止条件，避免模型、工具和状态逻辑相互耦合。

## 今天交付了什么

- 完成项目计划文档，明确 20 天 MVP 的目标、范围、每日任务和参考项目。
- 创建公开 GitHub 仓库并补充仓库管理文件，包括 MIT 许可证、贡献指南、`.gitignore`、Issue 模板和 PR 模板。
- 确定后续开发采用 GitHub Issue 和 PR 的方式：一个对话窗口只处理一个 Issue，每个 PR 默认只关联一个 Issue。

## 遇到的问题与解决过程

### 问题

一开始不清楚应该采用哪些具体技术路线，也无法判断成熟 ReAct 项目中的复杂能力是否应该在当前项目中引入。

### 解决过程

参考 ReAct 原始论文与实现，以及 LangChain、LangGraph、AutoGen、Semantic Kernel 等成熟项目的设计，重点观察模型调用、工具抽象、状态管理和测试边界。再结合本项目只有 20 天、目标是亲手理解 ReAct 主循环的约束，确定以下技术路线：

- 语言与包管理：Python `3.11+` 与 `uv`。
- 数据模型：Pydantic，用于校验模型输出、工具参数和执行轨迹等跨模块数据。
- 模型调用：优先通过 DeepSeek 的 OpenAI 兼容接口接入模型，并在业务层保留可替换模型服务的抽象边界。
- 测试：pytest，使用 Fake LLM 和确定性工具测试 ReAct 循环，避免测试依赖真实 API。
- 代码质量：ruff，负责格式化和基础静态检查。
- 配置：运行时代码从环境变量读取配置；本地 `.env` 文件不会提交，API Key 不会进入仓库。

技术路线是实现手段，而不是项目目的。当前阶段最重要的是实现并理解“推理或决策、执行工具、观察结果、下一轮决策”的 ReAct 闭环。
